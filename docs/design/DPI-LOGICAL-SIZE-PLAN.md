# DPI 逻辑工作区与截图策略计划（设计稿）

状态：已按 Windows DPI、代码兼容性、跨用户 replay 三路审查修订；测量、公共显式准备、尺寸门槛和截图输出选项已实现。经典 Paint 已在 144 DPI 实测迁移；其他 profile 迁移、跨用户实测与 replay 实现仍待后续工作。

## 当前实施结果（2026-09-23）

- `window.get` 在每显示器 DPI 感知的工作线程中返回目标显示器有效 DPI、窗口 DPI 感知方式、物理客户区和 `dip96` 客户区；公共 `get_window_state.layout` 只给出紧凑的逻辑客户区/DPI 摘要。若测量不可靠，不捏造客户区指标。
- profile v1 保持原值含义，发现与执行改用同一个宽度门槛；新增 v2 协议，用实测客户区的宽和高检查 `minimumClientSize`。经典 Paint 在 144 DPI 一次性窗口实测后迁移为 v2；新版 Paint 和 Aseprite 的客户区门槛仍待对应版本实测。
- `execute_batch` 增加独立的 `prepare_window` 动作，显式指定期望/最低 `dip96` 客户区；内部 `app.launch` 对 v2 profile 使用同一准备能力。普通观察不会调整已有窗口。
- `get_window_state` 新增 `max_edge`；整窗默认 1600，region 默认保留原始像素。PNG/WebP 选择及默认路径返回行为保持原样。
- 核心非交互测试在独立构建目录 19/19 通过；144 DPI 的一次性测试窗口请求 600×400 `dip96` 后实测为 900×600 物理客户区。超出工作区的请求返回 `insufficient_display_space`，没有调整窗口。144 DPI 的临时空白经典 Paint 在 v2 推荐尺寸启动后匹配 profile，实测客户区 1185×923；请求 1085×650 时应用实际保持 1085×680，profile 仍匹配。尚未验证 96/120 DPI、其他显示器及新版 Paint/Aseprite 的 v2 迁移。

## 目标与边界

目标是减少窗口尺寸和显示缩放变化造成的语义操作失败，使 profile 可在满足条件的不同用户环境中复用，并为未来的 replay 提供可检查的环境前置条件。截图输出尺寸和编码单独设计，用于控制传输与视觉质量。

本计划不保证像素级复现，也不通过读取窗口状态自动调整用户已有窗口。公共 MCP 工具仍为 `list_windows`、`get_window_state`、`execute_semantic`、`execute_batch` 四个；任何公共字段调整都以 `AgentApi::tools()` 为唯一 schema 来源。

## 术语与坐标契约

| 名称 | 含义 | 用途 |
|---|---|---|
| 屏幕物理像素 | 实际显示器、截图和输入坐标的像素 | 保留现有截图及基础输入映射 |
| 窗口外框物理尺寸 | 标题栏、边框、客户区合计的窗口矩形 | `SetWindowPos` 的目标；不直接代表可用布局 |
| 客户区物理尺寸 | 应用可绘制的客户区实测尺寸 | 换算逻辑尺寸，检查实际可用范围 |
| 96-DPI 逻辑客户区（本文称 `dip96`） | 以显示器有效缩放归一化后的客户区尺寸 | profile 的布局目标和最小门槛 |
| 应用布局/画布坐标 | 控件、文档、画布自己的坐标 | 语义动作；由适配器在运行时定位和换算 |
| 截图输出像素 | 编码后的预览图宽高 | Agent 视觉输入；与布局要求无直接关系 |

`dip96` 是 DesktopPilot 对跨显示器布局要求的**自定义归一化指标**，不是目标应用内部布局单位，也不承诺所有应用都按 Windows DPI 等比例布局。自绘、DPI 不感知、系统感知、每显示器感知的应用都须用当前客户区和控件证据复核；画布缩放另行检查。定义 `clientDip96 = physicalClient × 96 / monitorEffectiveDpi`，前提是已可靠取得目标显示器的有效 DPI。记录显示器标识及其 DPI、目标窗口 DPI 感知方式、窗口报告 DPI 和实际客户区尺寸；不把 `GetDpiForWindow(hwnd)` 单独当作显示器缩放：DPI 不感知窗口可能报告 96。实施前须选定并验证在当前 DPI 感知上下文中取得 `monitorEffectiveDpi` 的方法；无法确定时返回“DPI 证据不足”，不猜测逻辑尺寸。

例如显示器 150%（144 DPI）、要求 `1280×720 dip96` 客户区，估算需要 `1920×1080` 物理客户区，外框还需更多空间。因此 1920×1080 的物理屏幕通常容不下这一目标。`1920×1080 dip96` 在此缩放下约需 `2880×1620` 物理客户区，不能靠截图缩小解决。

## Profile 尺寸契约

建议在下一版 profile schema 引入明确字段，而不重解释现有字段：

```json
{
  "preferredClientSize": {"width": 1200, "height": 800, "unit": "dip96"},
  "minimumClientSize": {"width": 1050, "height": 650, "unit": "dip96"}
}
```

- `preferredClientSize` 是准备新窗口或用户明确要求调整窗口时的目标。仅供调整尺寸，不是兼容性充分条件。
- `minimumClientSize` 是开始需要展开布局的语义操作前的门槛。宽、高均需检查；缺少该字段的 profile 保留原有行为，直至显式迁移。
- 仅有最小尺寸也不能判定匹配成功；还须检查 executable、window class、支持的 DPI/布局模式、必需控件的唯一性、画布/缩放状态。自绘应用需要自己的可观察证据。
- 动作的画布坐标、归一化窗口坐标和 `dip96` 布局尺寸是不同概念。不得把已有动作参数或基础输入坐标静默改成 DIP。
- 同一 profile 对不同版本或语言界面不必强行通用；不满足条件时返回具体不兼容原因，而不是尝试盲点固定坐标。

迁移时核对现有 `recommendedWindow`、`minimumWindowWidth` 的原始单位与实测行为，再为每个 profile 写入新字段。不能把旧值简单重命名为客户区尺寸：`recommendedWindow` 当前是窗口**外框**目标。现有加载和部分执行代码只接受 `schemaVersion: 1`；实施时须明确旧版继续走旧语义、新版走新语义的双读/双执行路径，并同步更新加载、发现和各适配器。当前发现阶段按 DPI 缩放 `minimumWindowWidth`，经典 Paint 执行阶段却直接用物理宽度与该值比较，应统一判断路径；新版 Paint、Aseprite 的条件也要分别确认。固定像素操作（如 Aseprite 保存对话框坐标）在不同尺寸下仍有风险，不能靠此 schema 宣称可移植。

## 窗口准备与检查流程

1. **定位显示器与窗口。** 以窗口主要覆盖的显示器作为初始目标，记录显示器标识、工作区物理矩形（含原点）及有效 DPI；识别目标窗口的 DPI 感知方式。跨屏窗口明确记录所选显示器；调整后重新选取和测量，多显示器之间移动或 DPI 改变后不沿用先前结果。
2. **先判断是否需要调整。** 新启动且匹配 profile 的窗口可按显式推荐尺寸准备。已有窗口只在用户任务明确需要规范化尺寸，或未来 replay 明确包含此准备步骤时调整。`get_window_state` 保持只读观察语义，不暗中改变窗口几何。当前四个公共 MCP 工具没有启动/resize 动作；若要从公共接口调整已有窗口，实施前须选择现有工具中的明确动作入口并更新 `AgentApi::tools()`、文档和测试，或将准备步骤限定在内部启动/replay 流程，不能假定已有公开能力。
3. **按客户区目标计算外框。** 在 DesktopPilot 每显示器 DPI 感知的工作线程中，将 `dip96` 目标换算成该显示器的预计物理客户区；按目标窗口感知模式处理初算。`AdjustWindowRectExForDpi` 可估算标准 Win32 外框，自定义标题栏及 Windows DPI 虚拟化可能使估算有偏差。测量 `GetWindowRect` 与 `GetClientRect`/客户区屏幕位置时必须维持一致的物理坐标上下文；前者还包含不可见调整边框，不能直接当作可见截图边界。应用可能限制最小/最大尺寸，因此调整后必须重新实测，不能把 `SetWindowPos` 成功当作目标达成。
4. **处理放不下。** 优先尝试不超过显示器工作区的目标；不静默将推荐值裁剪后返回成功。实测值若低于 `minimumClientSize`，报告 `insufficient_client_area`，给出目标、实际、显示器工作区、DPI 和原因。不要自动降低系统缩放或分辨率。
5. **校验布局。** 重新读取窗口 DPI、外框/客户区、UIA 或视觉定位证据。检查必需控件、工具栏展开、画布可见、文档缩放和滚动等 profile 要求；这些控件证据优先于 `dip96` 推算值。尺寸达标但证据不匹配仍拒绝语义执行。
6. **执行期间监测。** 窗口移动、外框/客户区尺寸、DPI 或布局变化时使旧观察失效，重新检查后再继续。现有观察主要比较外框；实施时需把 DPI、客户区和必要布局证据纳入重验条件，覆盖外框不变而内部布局改变的情况。模态框和部分执行按照现有语义报告处理，不自动重放已派发动作。

建议返回结构（示意，不是已实现 API）：

```json
{
  "status": "error",
  "code": "insufficient_client_area",
  "requested": {"preferred": [1200, 800], "minimum": [1050, 650], "unit": "dip96"},
  "actual": {"clientDip96": [1000, 610], "clientPhysical": [1500, 915], "windowPhysical": [1516, 954]},
  "display": {"id": "display-1", "dpi": 144, "workAreaPhysical": {"x": 0, "y": 0, "width": 1920, "height": 1040}},
  "next": "Use a larger work area or a profile/action that supports this layout."
}
```

具体 Win32 计算须覆盖不可见调整边框、菜单、自定义标题栏、最大化窗口和应用内部限制。以“调整后实测客户区”作为最终事实；复杂窗口可进行有上限的修正，不进行无限 resize 循环。

## 截图策略独立于窗口准备

截图从实际物理区域捕获，再按请求的输出尺寸缩小。保留当前最长边 1600 的默认策略；如某个视觉任务确需 1920×1080，应显式请求更高输出尺寸，且不放大原图。不能总是除以 `displayDpi/96`：当前 2880×1620 的窗口按 150% 缩成 1920×1080，反而大于现有 1600×900 默认输出。细字、像素画和自绘界面可要求原尺寸局部截图。

`capture.bounds` 始终是物理截图范围，`capture.width/height` 是输出图片像素。基础输入继续用这两个量将图中坐标映射回物理坐标，不把截图像素与 `dip96` 混用。输出路径默认、内联图片按需请求。当前编码默认 PNG、`DP_IMAGE_FORMAT=webp` 可选；若将 WebP 改为默认，需要宿主能力协商或兼容性验证。编码选择只影响字节量/兼容性，不改变布局匹配。

当前缩图前还会写出一份全尺寸 `.original.png`。它不进入默认 MCP 响应，却增加本地磁盘和编码开销；截图阶段需单独评估是否保留、保留多久以及局部放大需求，不能将减少网络字节误写成同时减少了本地开销。

## 对跨用户 profile 与未来 replay 的作用

共享 profile 应记录已验证的应用版本、界面语言、DPI/布局范围、必要控件和画布条件。尺寸规范化使同一组控件更容易保持可见；每次运行仍须重新匹配。对固定像素坐标的动作，先改为控件定位、相对布局或视觉定位；无法定位则明确限定适用环境，不能纳入“跨用户可移植”承诺。

未来 replay 应记录语义动作和其输入、应用/文档前置状态、profile 内容哈希或发布版本、DesktopPilot/适配器版本及必要 OCR/视觉模型版本、窗口布局要求、每步可判定的后置条件和执行回执。文档前置状态至少区分新建/已有文档、文档身份与内容基线、画布尺寸、缩放/滚动、工具/颜色/选区、未保存状态、模态框及输出文件是否已存在；播放前须满足兼容矩阵。播放时重新发现窗口与控件，不持久化会话内的 `window_id`、`control_id`、`imageRef` 或截图点。每步等待界面稳定并检查后置条件，再进入下一步；分别记录派发状态、工具回执和可观察效果。`completed` 仅代表之前的动作返回成功，`failedIndex` 指向的失败动作本身可能已经产生部分副作用。遇到 `possibly_partial` 或结果不明时，先核验界面/文件，再按动作专属策略决定跳过、补偿或交由用户处理；不得自动从 `failedIndex` 续播，也不自动重放整段。UI 自动化动作可能受异步布局和应用逻辑影响，因此承诺“条件满足时可重复执行并可诊断失败”，不承诺任意机器像素级一致。

## 实施顺序与验收

1. **测量与契约：** 先验证有效显示器 DPI 的获取路径与物理坐标测量上下文，再增加窗口/显示器 DPI 感知方式、物理客户区及 `dip96` 观测；保留既有物理坐标字段语义。对 100%、125%、150%、200%，DPI 不感知、Unaware GDI Scaled、系统感知、Per Monitor V1/V2 窗口做换算测试；无法可靠测量时明确拒绝推算。
2. **统一门槛：** 抽取 profile 尺寸判定为单一逻辑，发现和执行共用；补宽高边界测试，修复现有经典 Paint 判断不一致。按 profile 实测迁移字段，不推断未经验证的新版 Paint/Aseprite 参数。
3. **显式准备：** 只在新启动窗口或明确请求时计算外框并调整，返回实测尺寸和不达标原因；测试小屏、多屏/混合 DPI、任务栏、最大化、不可调整大小的窗口。确保观察本身不 resize。
4. **截图选项：** 在保持 1600 默认和物理坐标映射的前提下加入可请求的输出尺寸；对局部无损截图、PNG/WebP、路径/内联和坐标回映做测试。评估文件字节、图片尺寸、视觉识别质量，分别报告，不把文件字节直接等同于 token。
5. **Replay 前置设计：** 固定相同应用版本/语言、文档基线和语义序列，在至少两个 DPI/工作区环境重复运行，并预先规定每格重复次数及通过门槛。分别统计不兼容环境被正确拒绝的比例、每步后置条件及最终视觉/文件结果达成比例、失败后无重复副作用比例；加入异步弹窗及失败步骤的中断恢复案例。实现 replay 前先确定状态快照格式和动作专属恢复规则。

每阶段使用 core CMake preset 构建和 `ctest --preset core-only -LE interactive`；需真实桌面验证的案例单列交互验收，不拿 mock 测试代替跨用户稳定性。若改公共 MCP 参数或返回结构，先修改 `AgentApi::tools()`，再同步生成 `docs/AGENT-API.md` 并更新示例和测试。
