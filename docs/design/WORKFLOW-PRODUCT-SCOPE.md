# DesktopPilot 编排：产品定义与首版范围

日期：2026-09-25。状态：首版文件批次 CLI 已实现并完成本机验收；产品场景仍为设计假设，未经过外部用户访谈验证。

当前可用能力与操作方法见 [使用指南](../guides/WORKFLOW.md)，测试证据见 [验收记录](../validation/WORKFLOW-ACCEPTANCE.md)。已交付 Aseprite 单帧 PNG 导出、逐项可信 JS 决策、暂停/取消、项目边界恢复与显式核对。下文的多规格产物、人工编辑接管和跨应用场景仍属于后续设计，暂停不代表允许修改源文件后认可新基线。

本文先定义用户要完成的任务，再约束技术设计。与 [动态编排设计稿](DYNAMIC-WORKFLOW-DESIGN.md) 存在阶段差异时，以本文的首版范围为准；技术稿中更广泛的 async 恢复、外部决策和跨应用能力属于演进方向。

## 1. 我们要做什么

为 Windows 桌面任务提供一个由 Agent 制作、用户可运行的流程系统：把一项明确的处理规则应用到一批输入，逐项验证结果，记录进度，并在异常后从可靠的项目边界继续。用户可以把成功的规则保存下来，换一批输入再次运行。

价值有两类：一次性长批次减少漏项、盯守与重做；重复任务减少重新解释、重新探索和维护操作步骤的成本。不能把“必须重复很多次”作为唯一使用条件。

首版主用户是个人创作者和独立游戏开发者；主任务是素材文件处理与导出。Agent 是流程作者，用户是规则提供者、运行者和结果检查者。同一个人可以兼任作者。当前优先同一用户、同一机器、一个交互桌面；不把多人管理、远程调度与异机兼容加入首版承诺。

我们交付的是完整的“定义规则 → 小样验证 → 批量运行 → 处理异常 → 查看产物 → 再次使用”体验。JS 是内部作者工具，不要求普通用户学习 JS。

## 2. 证据与假设

已经确认的上下文：项目具备 Node 业务层、四个 MCP 工具、Delta 和固定 Replay；用户希望动态编排，并关注实际用户场景。首版已通过 Aseprite 后台 CLI 建立单帧文件导出与产物验证闭环；GUI 批量打开、编辑器文档身份与未保存状态仍未形成完整语义闭环。

以下是设计假设，不是访谈结论：素材处理是最合适的首个用户任务；用户更看重结果、异常定位和继续执行，而不是编排语言；“Agent 生成一次规则 + 用户少量校正”的制作成本能在批次中收回。开发过程必须验证这些假设，没有依据编造用户规模、频率或节省比例。

## 3. 用户与场景地图

| 用户 / 场景 | 具体请求示例（虚构，用于设计） | 主要问题 | 能力与边界 | 优先级 |
|---|---|---|---|---|
| 独立游戏美术：素材导出 | 将一批单帧源文件导出为 PNG，保留透明背景并按规则命名 | 重复操作、命名错误、漏导出 | 文件清单、产物验证、逐项结果 | 首版主场景 |
| 创作者：多规格交付 | 每张图片产生原尺寸和 2 倍尺寸两份副本 | 多产物对应关系、部分交付 | 一项多产物、缩放方式、整项验收 | 主场景后紧接验证 |
| 用户：一次性历史素材整理 | 处理几十个旧文件，遇到不支持的先列出来 | 输入不一致、长批次容易遗漏 | 预检、分类、局部失败与继续 | 首版变体 |
| 创作者：增量重导出 | 只处理上次之后改过的素材 | 同名旧产物容易误判 | 源摘要 + 流程版本 + 参数 + 产物证据 | 首版只复用本次完成记录；跨批次缓存后置 |
| 音频/视频制作：批量输出 | 按预设输出多个文件，保留项目源文件 | 渲染时间长、插件与项目状态复杂 | 长等待、导出范围、音轨/时长验收 | 后续能力包，不宣称现成 |
| 办公人员：模板文档 | 按一张清单生成文件并导出 PDF | 字段映射、字体/分页差异 | 模板契约、结构/渲染验收，优先文档 API | 后续第二类产物任务 |
| 办公人员：跨系统填表 | 读取来源记录并填入另一软件的草稿 | 错配记录、重复写入 | 业务主键、写前/写后回读 | 后续；正式提交需独立设计 |
| 运营人员：批量上传发布 | 上传附件并发布一批条目 | 网络不确定、公开副作用 | 服务端回执、授权、去重 | 首版范围外 |
| 开发/测试人员：重复检查 | 在多个测试文件中操作并比较截图 | 环境漂移、误判通过 | 可复现环境、测试断言、失败证据 | 内部验证用途；不是首版市场承诺 |
| 研究/工程人员：旧软件数据输出 | 在只能点界面的工具里逐个导出结果 | 等待时间长、输出难关联 | 输入输出关联、应用专用验证 | 后续能力包 |
| 用户：半自动创作 | 每个方案先由我调整，再自动导出和归档 | 人工判断与机械操作交替 | 暂停、接管、认可新基线 | 首版支持项目间接管；项内恢复受能力限制 |
| 高频办公用户：定时日报 | 每天自动打开工具取数据形成报告 | 定时、登录状态、桌面可用性 | 调度、凭据、无人值守环境 | 首版不承诺锁屏/未登录执行 |
| 高级用户：流程交接 | 把已验证规则给同事使用 | 版本、字体、路径、应用配置不同 | 可移植包、兼容性检查、试跑 | 首版同机复用；异机分享后置 |

这些场景共有输入、规则、执行、验收、异常和产物；专用应用能力仍需分别建设，不能仅添加一个 profile 就宣称支持整类任务。

优先级依据为：任务是否明确、结果能否验收、是否可保护源数据、实际操作基础与实现成本。没有用户量与工时数据，因此本阶段不使用虚构的 RICE 分数。

## 4. 谁负责什么

| 角色 | 负责 | 不能默认承担 |
|---|---|---|
| 用户 | 说明目标、输入和业务偏好；查看需要判断的结果 | 阅读 JSON 日志、判断派发状态、写恢复代码 |
| Agent / 作者 | 探索可行路径、生成流程、提炼变量、补充验收、解释异常 | 默默替用户决定未说明的覆盖/发布规则；把一次成功当全面验证 |
| 应用能力包 | 打开/绑定文档、处理/导出、检查内容、恢复到下一项起点 | 用动作回执证明业务结果；跨不兼容版本盲点坐标 |
| 运行器 | 固定输入和版本、串行派发、保存记录、维护状态、控制继续 | 推断任意软件的未保存内存；自动撤销任何副作用 |

Agent 由现有宿主提供，首版不内置新的模型服务。运行已确定规则不需要每个动作都问模型。需 Agent 协助时生成具体异常材料，由现有会话接手。

## 5. 主场景的完整定义

首个真实业务流程：在选定且验证过的 Aseprite 版本上，将一批单帧 `.ase` / `.aseprite` 文档的可见合成内容，按约定导出成 PNG 副本。首版尺寸默认保持原样、透明度保持原样；缩放作为后续同场景增量。隐藏图层、色彩模式等通过明确导出契约和实际验收定义，不能默默采用未知应用设置。

动画/多帧文件在首版标为不支持并列出，不静默只导出第一帧。贴图集、帧标签导出、逐层导出和调色板变换属于后续模板。

示例请求：

> 把这个文件夹里的单帧素材导出为 PNG，放到新目录，保留相对目录。不要改源文件，不支持的列出来。以后还要对别的文件夹使用同样规则。

用户应能经历如下过程：

1. 提供目标、文件夹和输出位置。系统扫描后固定本次清单；同名文件通过相对目录区分。
2. 展示预计处理、明确不支持、需打开后确认的项目。扫描后新增文件不自动加入本次任务。
3. 显示规则卡：输出命名、是否覆盖、支持范围、使用桌面的阶段、验收方式。
4. Agent 在独立样本输出目录做小样，覆盖输入中的代表性差异；将必要的界面路径补成应用能力。不是用已有输出假装已测试。
5. 用户已明确授权且规则无歧义时继续批量执行；只对未明确的业务选择提问，不增加每步确认。
6. 执行时显示当前文件、最近产物、完成/失败/跳过/未决/未开始数量；不承诺不可靠的剩余时间。
7. 异常时给出证据和可用选择。确认失败仅影响当前项且应用已恢复到起点时，才能按预设策略继续下一项。
8. 完成后列出结果与未完成项；用户可以打开产物或从待处理项派生新批次。
9. 保存流程及适用范围，下一次更换输入后重新预检，无需重新讲述全部操作。

源文件不覆盖；批次默认使用新输出目录。应用存在用户未保存的文档时必须避让或暂停明确处理，不关闭或保存用户文档作为准备步骤。

## 6. 产品对象与最小界面

只向普通用户暴露四个核心对象：

- **流程**：处理规则、适用应用/版本、可填参数、支持/不支持的输入、如何判断完成。版本不可原地改写已发生的运行。
- **批次**：这一次的输入清单、参数、输出目录、执行记录和汇总。
- **项目**：一个输入及其全部产物；是首版进度和恢复的业务单位。
- **产物**：输出文件与验收证据，关联输入与参数，区别于临时截图和诊断日志。

首版用户界面需要规则卡、批次进度、异常卡和结果清单。可先通过现有 Agent 对话 + CLI 结构化状态 + 本地可读报告呈现，不以建设独立桌面壳或拖拽编辑器作为前置工作。

```text
流程：单帧素材导出 v1       批次：characters-02
36 项：完成 24 | 失败 1 | 跳过 2 | 待核对 1 | 未开始 8
当前：boss/idle.aseprite
状态：检测到输出文件，但导出参数无法确认；已暂停

查看输出    查看证据    接管桌面    停止批次
核对完成并满足继续条件后，再显示“继续”或“重新处理当前项”
```

必须明确集成入口：开发者/具备本地命令能力的 Agent 使用 Workflow CLI 启动、查询与控制，命令返回 runId 和结构化状态；非技术用户通过 Agent 会话操作。仅能使用四个 DesktopPilot MCP 工具的宿主，首版不能直接管理 workflow，不伪装成 execute_batch 支持任意脚本。若以后需要纯 MCP 工作流入口，应单独讨论协议版本。

任务进程由宿主控制并保留状态。首版不承诺关闭宿主后继续运行；进程退出后仍保留项目记录，重启后可核对并继续。

## 7. 从一次操作到可复用流程

不能把操作录像直接标为成熟流程。制作过程需要产出三样内容：参数化规则、能力要求、结果契约。

制作阶段：草稿 → 样本通过 → 本次批次验证 → 可供同环境复用。展示实际通过的输入和环境范围，不使用笼统“稳定”标签。

Agent 从轨迹中剔除探索、失败和纠错步骤；把文件名等本次值提为参数；识别有业务意义的弹窗；声明不支持的情况。清楚区分用户明说、应用默认、Agent 推测的规则，只有会改变结果且无法推断的选项才询问。

试跑样本依据输入特征挑选：例如透明图、不同尺寸、含中文或空格的路径、嵌套目录；仅选首文件不构成代表性覆盖。具体样本数由差异决定。小样通过后全批仍逐项验证。

修复流程生成新版本，旧运行保留原规则。首版从未开始或已明确失败的项目创建新批次；结果未知的项目先核对。不要让“修复后再跑”悄悄重做已成功项目。

## 8. 执行路径选择与应用适配边界

对每个业务动作优先检查已安装且可验证的 CLI/API 能力，其次使用匹配的桌面语义能力，再考虑受控基础输入。不能为了展示桌面自动化而绕过更可靠的后台接口，也不能假设应用必然有可用 CLI。

首版只内置为主场景验证过的应用路径；不顺便建设通用连接器平台。调用外部程序属于带固定程序/参数/输出契约的宿主能力，不把任意 shell 回调包装成可恢复动作。

如果主场景可完全通过可靠 CLI 完成，采用该路径并测量相对直接 CLI 脚本的增益。进度、参数化、核验和异常处理不能带来实际收益时，应简化产品投入，而非强行插入 UI。共享桌面内核另用至少一个真实需要 GUI 的窄场景验证，不能用 Paint 成功替代 Aseprite 的应用验收。

环境预检检查应用版本、能力、输入可读性、输出可写性、目标唯一性及交互桌面可用性。可静态发现的失败在执行前报告；依赖打开文档才能发现的情况标为待运行确认。文件预检不能证明所有后续权限/磁盘/应用状态永远不变，运行中仍检查。

`validate/plan` 只读取声明和文件，不加载流程 JS，也不抢占桌面；现场探测和样本执行明确属于操作阶段。每次批次记录应用、适配器和运行时版本；版本或配置变化后重新判断兼容性，不因上次成功而直接派发。运行中首次命中已授权范围内的分支正常执行；超出原任务范围或无法判断时才询问，不为每个分支增加确认。

## 9. 状态、失败与恢复的用户契约

| 发生什么 | 展示什么 | 首版允许的处理 |
|---|---|---|
| 输入格式不支持 | 跳过及原因 | 不改变文件，按策略处理下一项 |
| 输入自扫描后改变 | 输入已变化 | 当前项停止，重新纳入新批次，不用旧摘要继续 |
| 未派发且打开失败 | 当前项失败，未产生修改 | 清理到已验证起点后，可重试当前项或继续其它项 |
| 输出存在但验收不通过 | 输出不符合规则 | 保留到异常目录；不记完成、不把源文件视为已处理 |
| 已派发、结果不明 | 待核对 | 停止桌面链，核对产物与文档状态；不自动点击重试 |
| 用户要求暂停 | 正在暂停 / 已暂停 | 默认当前项目完成或到显式安全边界后让出桌面 |
| 用户要求立即停止 | 已请求停止，当前项可能待核对 | 停止后续派发；不得宣称已撤销输入 |
| 应用崩溃或系统锁屏 | 等待恢复环境 | 环境就绪后重建当前项或人工核对，不循环点击 |
| 用户修改未开始项参数 | 将创建新的剩余项批次 | 已完成项仍关联旧参数，当前未决项单独处理 |

首版承诺保存已经验收的项目结果，并据此避免无依据地重复执行；不承诺恢复应用的任意内存状态或每一次鼠标操作。

当前项只有在源文件可重新打开、源状态未改变、临时产物可隔离且能力包提供重建规则时，才允许整项重新处理。项目间连续运行需要证明上一个失败未遗留错误目标、模态框、选区或剪贴板依赖。项目失败不必总停整批，但未知结果必须暂停相关执行链。

业务成功与机器验收分开：尺寸、格式和文件存在只能证明对应要求；完整像素比较适用于具有参考结果的任务，不能证明艺术质量。无独立内容证据时标明“导出完成，已检查格式/尺寸，内容待检查”，不伪装成完全验收。

## 10. 文件与结果策略

- 默认每批次新输出目录，保持源相对目录。输入中不同子目录的同名文件不合并。
- 已存在的同名文件默认冲突；首版不因存在文件而跳过。只有本次日志记录的已完成项目且证据仍有效，才作为完成结果复用。
- 临时导出与最终产物区分；导出后完成验证和产物登记才标记项目完成。不能保证应用支持原子保存时，不承诺原子性。
- 一项多输出必须全部满足规则才标项目完成；缺一份时记录部分产物，避免把文件数误当完成项数。
- 源身份、源摘要、流程版本、参数摘要和产物摘要共同建立关联。修改时间或文件名只能辅助识别。
- 结果报告含未完成项与原因；不自动清理未知或失败产物。用户可据此选择后续处理。
- 日志和截图默认保存在本机，显示存储位置；不默认上传源内容。分享包与诊断包后续增加明确的内容选择，防止完整桌面截图被无意包含。

## 11. 首版与后续范围

| 首版必须交付 | 紧接验证 | 后置 |
|---|---|---|
| 固定输入清单、规则参数、环境与能力预检 | 多规格/一项多产物模板 | 无限制跨应用任务 |
| 一个真实素材导出能力闭环 | 同类模板文档产出 | 发布、发送、支付等外部提交 |
| 逐项状态、产物关联、明确验收范围 | 跨批次的增量处理 | 自动从所有未知界面学习能力 |
| 已知条件分支、有界循环、超时 | 有界 Agent 异常协助 | 任意 async JS 的自动恢复保证 |
| 安全暂停、接管、停止、项目边界继续 | 增强项内恢复 | 通用工作流图编辑器 |
| Agent 制作与小样验证、同机保存复用 | 另一应用的 GUI 必需场景 | 无人登录/锁屏桌面自动运行 |
| 可信 JS 作者接口、CLI 状态与控制 | 更友好的本地运行面板 | 团队权限、云调度、共享市场 |

JS 动态性服务于有限分支、输入循环和处理策略；首版不接受任意未申明外部副作用，也不需要一开始完成全部异步历史回放功能。项目内失败可停止并按规则重建，项目外持久化进度；日志仍保存动作 intent/receipt，以防把未知动作误判为可重跑。技术选择不得扩大上述恢复承诺。

## 12. 开发顺序：按完整任务推进

1. **能力验证**：确认主场景实际可用的 CLI/API/GUI 路径，完成一个文件从源到输出的验证。能力无法成立则先修能力，不能用编排 UI 掩盖。
2. **完整窄批次**：固定规则处理多个文件，具有清单、逐项验收、报告和异常停机。此时可内部使用，无需通用作者 SDK 已完工。
3. **可靠继续与控制**：run lock、项目检查点、剩余项执行、暂停/停止/接管、未知结果核对、源变化和产物冲突。
4. **动态与制作体验**：受控 JS 接口、小样、已知条件分支、规则保存、换输入复用。先覆盖主场景真实变化。
5. **第二类任务检验抽象**：选择文档产物或另一需要 GUI 的窄任务，检查是否只需增加能力，而不用重写运行器；再决定更广泛的动态恢复与界面投入。

不先写一套完整通用引擎，再寻找任务。每个阶段都有可运行的业务产物和限制说明。

## 13. 验收与是否值得继续

以下为拟议验收，不是已经达到的结果：

### 功能验收

- 用不少于 20 个输入组成真实批次，覆盖不同尺寸、透明内容、中文/空格路径、嵌套同名文件，以及明确不支持/损坏输入。
- 所有输入都有最终状态；不漏项、不把跳过/未决计作成功。可处理项的输出满足各自验收契约，源文件摘要不变。
- 在项目间中断：恢复保留已验收项的完成记录和有效产物，不重复派发这些项。
- 在项目内派发后中断：标待核对，不能盲重跑；能够重建的项目按独立规则和新 attempt 执行。
- 用户暂停并使用桌面后，可在重验通过时继续；存在用户未保存文档、模态阻挡或环境变化时明确停住。
- 两个进程不能同时执行同一批次；多个协作运行器不能同时使用同一输入桌面。
- 换一个包含同类输入的新目录，使用同一流程参数再次完成，无需重写流程。

### 用户价值验收

分别记录制作时间、人工盯守/处理时间、桌面占用时间、总耗时、Agent 调用/token、最终可用产物和未决项。对比人工/Agent 从头做；有可靠 CLI 的场景还要对比直接脚本。所有方式使用同一任务和同一验收契约。

重复使用的价值需计入制作和维护成本。若每批节省的人工时间为正，可估算回本批次为“制作与维护时间 / 每批人工时间节省”；为零或负时不宣称能回本。一次性批次则直接比较本次全过程的人工投入和结果质量。

继续投入的依据：换输入后用户确实减少重复说明和盯守；异常可按项目定位；恢复没有引入重复写与静默遗漏。若只减少点击而增加更多核对工作，应调整场景或能力，而不是用执行步数/节点数证明价值。

## 14. 仍需在真实样本中验证的决定

这些问题不阻塞当前范围确定，但会影响后续取舍：主应用版本和可靠路径；输入中静态/动画比例；用户最常用的命名与输出规则；典型批次规模；用户愿意让出桌面的时间；什么证据足以认可产物；流程制作成本是否低于重新执行。

先以同机、单帧、新输出目录、不改源文件、项目边界恢复为默认，使用真实素材样本收集证据。若样本表明用户主要需求是动画贴图集，应调整主流程契约，并同步验收，不能沿用单帧流程的成功记录宣称覆盖动画。

## 15. 本轮评审取舍

产品评审提出跨应用填表和 GUI 回归也可作为 P0；本稿没有同时接受这些优先级，因为它们需要不同的应用能力、记录身份和验收契约。首版保留文件产物型任务，第二类场景用于验证抽象是否可扩展。

架构评审建议明确 CLI、现场探测、版本绑定与中断处理，已纳入。试跑和运行不增加机械的“第一条写操作”确认：用户原任务已授权且范围明确时继续；仅在确需决定业务规则或实际权限边界时询问。流程作者可以使用可信 JS，但用户获得的恢复承诺由能力与项目边界决定，不由脚本语法决定。
